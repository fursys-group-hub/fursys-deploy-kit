---

사용자가 `/deploy2` 를 실행했다. 앱을 **2번 서버(운영 2호기)** 에 처음 올리는 작업을 시작한다. 기본 `/deploy` 와 올리는 곳만 다르고 나머지 절차는 똑같다.

**`deploy` 스킬을 사용해** 처리하라. 스킬의 절차를 그대로 따른다:
- 사용자에게 묻는 건 **딱 두 가지**(① 어느 브랜드/공간, ② 접속 주소 앞부분). 그 외는 자동 처리.
- 키 확보 → 전송 대상 가드 → GitHub 올리기 → 로컬 검토 게이트 확인 → `scripts/deploy.sh` 로 생성·폴링 → 실패 시 `scripts/logs.sh` 로 원인 해설.
- 배포 **가능 여부 검토** 요청("배포해도 되는지/다시 검토")은 이 스킬이 아니라 `security-review` 스킬(배포 전 검토)로 안내한다.

**2번 서버(운영 2호기)에 올린다 — `/deploy` 와 다른 점은 아래뿐이다:**
- **배포 실행 시(스킬 ⑥) `scripts/deploy.sh` 에 `--server coolify-oper-web-2` 를 항상 붙인다.** 이 플래그가 앱을 2번 서버로 올린다. 다른 인자·플래그(주소 앞부분·포트·설정값·볼륨 등)는 `/deploy` 와 동일하게 넣는다.
- **접속 주소 안내는 `{앞부분}.app2.hub.fursys.com` 으로 한다**(1번 서버의 `{앞부분}.app1.hub.fursys.com` 이 아니다). 예: 앞부분 `event` → `event.app2.hub.fursys.com`. 확정 주소를 사용자에게 그대로 보여주고 확인받는다. (쉬운 설명: "이 앱은 **2번 서버(운영 2호기)** 에 올라가고, 주소는 `{앞부분}.app2.hub.fursys.com` 이에요.")
- deploy.sh 가 `SUBDOMAIN_RESERVED` 를 주면(관리자가 접미사를 공유 공간으로 바꾼 특수 설정에서만 발생) 이렇게 안내한다: "그 주소 앞부분(`○○`)은 시스템이 예약해 둔 이름이라 쓸 수 없어요. 다른 한 단어로 정해 주세요." 그리고 다시 주소 앞부분을 받아 진행한다. deploy.sh 가 `SERVER_UNKNOWN` 을 주면 "2번 서버를 찾지 못했어요. IT본부에 문의해 주세요." 라고 안내하고 멈춘다.

**검토 게이트·설정값 수집을 비롯한 나머지 규칙은 `/deploy`(deploy 스킬)와 100% 동일하다** — GitHub 올라감 확인, Dockerfile 빠른 확인, 로컬 검토 게이트(`last-verdict.json`) 확인, 검토 결과 서버 등록, 생성·폴링, 실패 원인 해설, 마무리 안내까지 그대로 따른다.

모든 응답은 한글, 비개발자가 이해할 수 있게 쉽게.
